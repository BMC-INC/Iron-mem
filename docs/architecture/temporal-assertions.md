# Structured temporal assertions

Status: experimental, opt-in. The legacy memory model and search APIs remain available.

## Identity and meaning

A scope is the exact tuple `(namespace, project, subject, predicate)`. Namespace uses IronMem's canonical namespace spelling. Other strings preserve case; leading/trailing whitespace and control characters are rejected. Subjects are explicit identifiers such as `toolchain:rust` or `service:api`, not inferred aliases. `Rust`, `rust`, and a different project's `toolchain:rust` are different subjects. Callers must resolve ambiguity before writing.

Each immutable event contains a string value (or null for retraction), an existing evidence memory ID and SHA-256 of its summary, a validity interval, optional supersession target, recorded timestamp, actor, scope-local version, and previous event hash. The assertion ID is the SHA-256 of its canonical serialized event. This records an operator's structured interpretation; it does not claim the source proves that interpretation. It never rewrites existing summaries, memory IDs, governance hashes, or exact originals. No automatic prose merging or new authority is inferred.

`valid_from` and `valid_until` are Unix seconds and form a half-open interval. `recorded_at` and query `recorded_before` use Unix milliseconds. Recorded time is generated by the database-writing application, clamped to the preceding event's time; scope version resolves ties. An as-of query includes all events recorded at or before its cutoff. Two events in the same millisecond share that cutoff, while their versions remain ordered.

A write names the expected scope version, initially zero. Under one write transaction, IronMem checks that version, reads active scoped evidence, appends the event and its governance ledger receipt, and queues context invalidation. PostgreSQL uses the existing namespace ledger advisory lock; SQLite reserves its writer before reading. Rolled-back writes leave neither an event nor a receipt. A retry after a successful write receives a version conflict; there is no automatic replay of a request with an updated version.

The event sequence is the semantic delta journal for this feature. It is independent of operational row mutation counters and the incomplete legacy mutation ledger. Reading verifies the content hashes, contiguous versions, previous hashes, scope, and supersession references. Public APIs expose append and query only. Database owners can still alter their own database; this is not a cryptographic signature or a SQL administrator tamper-proof store.

## Current state, conflicts, and restrictions

Current pointers are derived on every query, including validity checks, rather than stored pointers that become stale when the clock advances. The selector first evaluates the complete visible-at-recorded-time event history:

- A value is eligible during its validity interval, until an explicit successor becomes valid.
- A supersession must name an earlier value in the same scope and cannot start before its target. It suppresses that target from its own valid start onward, including after the successor expires. The old claim does not silently become current again.
- A null value retracts the named target. Retractions do not erase history. To reinstate a value, append a new assertion explicitly.
- Independent overlapping claims coexist. Multiple eligible claims, even with equal strings, yield `conflict` and no current pointer. Popularity, arrival order and temperature never choose a winner.
- Retroactive corrections affect past valid time only for queries whose recorded cutoff includes the correction.

Every delivered event must still have active evidence in the same namespace and project, with an unchanged summary fingerprint, and pass today's influence/purpose gate. Historical queries do not bypass today's restrictions. Source-required claims are withheld from this summary-only endpoint; callers use the existing governed `retrieve_original(memory_id=...)` workflow. Denied, tombstoned, deleted, expired or changed evidence makes the affected result incomplete. Hidden successors still suppress old values: restriction never resurrects stale advice. Reasoning-only results are explicitly marked. A current pointer is returned only when exactly one claim is available and no candidate is withheld.

Existing correction mining and contradiction sets are unchanged. Structured assertions reference their evidence memories, so those memories' policy and contradiction gates still apply. An assertion conflict is not an automatic mutation of a legacy contradiction set. Callers can explicitly manage that set through the existing API.

## API

Add this field to local `~/.ironmem/settings.json` to enable the feature:

```json
{"assertions":{"enabled":true}}
```

Do not replace the other settings fields. Disabling the feature blocks assertion APIs without converting or deleting stored events. Default is false; no runtime settings are changed by building this feature.

CLI: `ironmem assertion '<JSON request>'`

REST: `POST /assertions` with the JSON request body.

MCP: `memory_assertion` with `{"request": <JSON request>}`.

Local operator channels have `assertions:read` and `assertions:write`. Configured remote principals require these explicit capabilities and the appropriate namespace allowlist; shared-token MCP gets neither implicitly. Request actor identity is server-derived, not supplied in the JSON. Normal bearer authentication and strict purpose attestations are unchanged.

First record the evidence using the existing `remember` API, then pass the returned real memory ID:

```json
{
  "op":"write",
  "scope":{"namespace":"local","project":"/workspace/example","subject":"toolchain:rust","predicate":"version"},
  "expected_version":0,
  "memory_id":42,
  "value":"1.80",
  "valid_from":1722470400
}
```

The example ID 42 must be replaced with the existing evidence ID. The response returns `id`, `version`, and `recorded_at`. To record a correction, use the next expected version, its own evidence memory, and `supersedes` equal to the earlier assertion ID. Set `value` to null with a supersession target for a retraction. Optional `valid_until` bounds a value's interval.

```json
{
  "op":"query",
  "scope":{"namespace":"local","project":"/workspace/example","subject":"toolchain:rust","predicate":"version"},
  "valid_at":1725148800,
  "recorded_before":1725235200000,
  "history":false
}
```

Omit timestamps for current time. `history:true` returns governed events known by the recorded cutoff; valid-time filtering is intentionally disabled for that history view. Queries accept the existing `purpose` envelope. Responses include the latest scope `version` for optimistic writes, effective cutoffs, `status` (`current`, `conflict`, `unknown`, `incomplete`, or `history`), optional `current_id`, and individually labeled assertions. The version is a concurrency token, not a claim that all history is authorized for the reader. Successful query delivery contributes recall telemetry once per distinct evidence memory; internal history reads do not.

## Recovery and compatibility

Full and incremental v5 checkpoints include the `assertion_events` extension. They carry exact evidence sources through the existing memory/source closure while evidence remains retained. Deleted evidence is not recreated by assertions. Governed deletion and project wipe remove live recall eligibility; immutable assertion values remain historical records, like retained snapshots and audit evidence. This feature does not provide physical history erasure. Source-free assertion history preserves only its reference and fingerprint and remains ineligible.

Independent exports verify row projections and complete per-scope chains, in addition to envelope hashes. Restore merges immutable local history with checkpoint history and validates the union. Identical events deduplicate; divergent same-version histories fail before replacement. Restoring an older checkpoint cannot erase newer assertions or rewind its concurrency version. Restored legacy evidence may leave a newer assertion unavailable; the API reports that rather than picking an older value. This differs deliberately from rewinding ordinary project content.

Older v5 checkpoints without assertions remain readable and preserve any live assertion history on restore. Incremental capture emits a new full base when its table inventory changes. Older binaries that reject the extension need a pre-upgrade backup to roll back. Global restore and destructive v4 restore remain blocked.

## Evaluation and enablement gate

Executable fixtures cover version updates, retroactive time, overlapping claims, retraction, ambiguity, concurrent writes, missing/restricted evidence, retained history, legacy v5 compatibility, full/incremental export and restore, and CLI/REST/MCP contracts. PostgreSQL runs the same temporal transaction contract and snapshot round trip. These are deterministic correctness tests, not scored natural-language accuracy results.

This first implementation retains full structured events plus existing evidence; it does not claim less storage than independent prose memories. Shared base scope and hash-linked deltas provide explicit semantics, but a dictionary encoding or compressed semantic payload needs a measured workload advantage. The feature remains off by default until paired temporal quality and end-to-end storage/latency results justify enabling it. No personal corpus, paid answer/judge run, production migration, or installed-runtime update is required for the local validation.
